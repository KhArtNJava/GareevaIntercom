# GareevaIntercom

Эксперимент с получением видеопотока от домофона/видеорегистратора (MDVR96NT_2_R) по TCP.
Клиент отправляет на устройство запрос из `toServer720.bin`, получает в ответ 500 КБ
потока H.264 и сохраняет его в файл.

## Состав

| Файл | Назначение |
|------|-----------|
| `socket_client.py` | Python-клиент: читает `toServer720.bin`, шлёт его на `192.168.31.150:9000`, принимает 500 КБ ответа и пишет в `fromServer.bin` |
| `toServer720.bin` | Запрос к устройству, 500 байт (см. ниже) |
| `fromServer.bin` | Сырой ответ устройства, 512 000 байт |
| `IntercomPlayer/` | Проект Blazor (.NET 10): HTML-плеер, приём потока, демультиплексор, ffmpeg → HLS |
| `PROTOCOL.md` | Описание протокола: поля запроса, ответ, формат кадров, что не установлено |
| `tools/build_request.py` | Генератор запроса с заданным каналом и типом потока |
| `raw.h264` | Видеопоток, вырезанный из `fromServer.bin` с первого SPS (смещение 568); проигрывается в VLC |

## IntercomPlayer (C# Blazor)

Веб-приложение в каталоге `IntercomPlayer/`: на главной странице HTML-плеер показывает живое видео со звуком.
Подробности и настройка — в [IntercomPlayer/README.md](IntercomPlayer/README.md).

```bash
cd IntercomPlayer
dotnet run --launch-profile http   # http://localhost:5280
```

## Python-скрипт: запуск

```bash
python3 socket_client.py
```

Файлы читаются и пишутся в каталоге скрипта. Параметры (`HOST`, `PORT`, `TARGET_SIZE`,
`TIMEOUT`, имя выходного файла) заданы константами в начале скрипта. Если сервер закроет
соединение раньше, чем придут 500 КБ, скрипт сохранит полученное и завершится с кодом 1.
Таймаут сокета 30 с.

Просмотр результата:

```bash
vlc --demux h264 --h264-fps 25 raw.h264
```

## Анализ `toServer720.bin` (запрос)

Подробный разбор — в [PROTOCOL.md](PROTOCOL.md). Кратко: из 500 байт значимы только первые 40 (big-endian поля:
команда, номер канала, тип потока), остальное — мусор из памяти клиента Windows (указатели), который устройство
игнорирует. Собрать запрос с другим каналом или потоком: `python3 tools/build_request.py --channel 1 --stream 0`.

## Анализ `fromServer.bin` (ответ)

- Размер 512 000 байт (500·1024), энтропия ≈ 7,9 бит/байт (сжатое видео).
- Заголовок потока (~528 байт): строка `MDVR96NT_2_R` (смещение 0x60), метка времени
  `1a 0b 0d 16 3a 2f` = 2026-11-13 22:58:47 (год-месяц-день-час-минута-секунда, по одному байту).
- Видеокадры упакованы с тегом `00dcH264` (как видеочанк AVI) и заголовком около 40 байт:
  длина данных, время кадра, разрешение (`c0 02 40 02` = 704×576).
- Видео: H.264 Baseline, yuv420p, 704×576 (D1/PAL), 25 к/с, около 1,2 Мбит/с.
- 7 ключевых кадров (по одному в секунду, 22:58:47–22:58:52), между ними 124 P-кадра.
  Последний кадр оборван лимитом в 500 КБ.
- Значение `0x1f40` (8000) встречается в заголовке дважды; предположительно параметр аудио (догадка).

## Формат кадров (подтверждён по захвату и в IntercomPlayer)

```
"NNdc"|"NNwb" (4)  тип кадра: dc — видео, wb — аудио (аудио в захвате не встретилось)
кодек ASCII (4)    "H264"
размер данных (4)  little-endian, без заголовка
флаги (4)          0x10 — ключевой кадр
метка времени (8)  микросекунды, монотонная (40000 между кадрами при 25 к/с)
[16 байт]          только у ключевого видеокадра: дата YY MM DD hh mm ss, fps, ширина, высота
данные             Annex B (00 00 00 01 ...), кадры выровнены по 8 байт нулями
```

Раньше в этом документе метка времени ошибочно названа «временем в мс»: на самом деле это микросекунды
от запуска устройства, а календарное время берётся из 16-байтового блока ключевого кадра.

## Известные ограничения

- В `raw.h264` между кадрами остались заголовки регистратора (`00dc...`, около 40 байт),
  поэтому возможны артефакты при воспроизведении. Чистый вариант получится после
  разбора контейнера по `00dc` с сохранением в `.mp4`.
- Протокол запроса не расшифрован: содержимое `toServer720.bin` не менялось.
- Файлы содержат видео с реального устройства, репозиторий должен оставаться приватным.
