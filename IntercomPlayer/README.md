# IntercomPlayer

Blazor Web App (.NET 10, Interactive Server). Открывает TCP-соединение с регистратором, отправляет файл запроса
(как `socket_client.py`), разбирает ответ, отделяет видео H.264 и звук и показывает их в HTML-плеере на главной странице.

## Как это работает

```
регистратор ──TCP──► StreamRelayService ──► MdvrDemuxer (кадры dc/wb)
                                                │ видео → IVF с метками устройства ─► ffmpeg (tcp, порт 1)
                                                │ звук (или тишина) ───────────────► ffmpeg (tcp, порт 2)
                                                ▼
                           ffmpeg: видео -c copy, звук → AAC, HLS (сегменты ~1 с) в каталог hls/
                                                ▼
                  браузер: <video> + hls.js (в Safari нативный HLS), адрес /hls/stream.m3u8
```

- `Services/MdvrDemuxer.cs` — разбор потока (формат описан в корневом README).
- `Services/StreamRelayService.cs` — подключение, отправка запроса, переподключение при обрыве, статистика.
- `Services/FfmpegHlsMuxer.cs` — запуск ffmpeg и подача в него данных.
- `wwwroot/player.js` — подключение hls.js и автовосстановление плеера; hls.js 1.5.20 лежит в `wwwroot/lib/hls/` (лицензия рядом).
- `Components/Pages/Home.razor` — страница с плеером и панелью состояния (обновляется раз в секунду).

Видео не перекодируется (`-c copy`), нагрузка на процессор небольшая. Задержка около 3–5 секунд (HLS).

## Требования

- .NET SDK 10
- `ffmpeg` в `PATH` (или путь в `Intercom:FfmpegPath`)
- Браузер с H.264: Chrome, Edge, Firefox, Safari. Chromium без проприетарных кодеков видео не покажет.

## Запуск

```bash
dotnet run --launch-profile http
```

Страница: http://localhost:5280 (профиль слушает на `0.0.0.0`, то есть доступна и по сети).
Хост, порт и прочее задаются в `appsettings.json`, раздел `Intercom`:

| Параметр | По умолчанию | Значение |
|----------|--------------|----------|
| `Host`, `Port` | `192.168.31.150`, `9000` | куда подключаться |
| `RequestFile` | `toServer720.bin` | файл запроса (относительно каталога приложения) |
| `AudioFormat` | `alaw` | формат звука: `alaw`, `mulaw`, `s16le` |
| `AudioSampleRate` | `8000` | частота дискретизации звука |
| `FfmpegPath` | `ffmpeg` | путь к ffmpeg |
| `HlsDirectory` | `hls` | каталог HLS-сегментов (не коммитится) |
| `ReconnectDelaySeconds` | `3` | пауза перед переподключением |

## Проверено

На реальном устройстве (канал DOOR1, 704×576, 25 к/с): видео воспроизводится в Chrome в реальном времени
(299 кадров за 12 с, пропущено 2), в HLS есть дорожка AAC, панель состояния обновляется.

## Ограничения

- **Звук не проверен на реальных данных.** В потоке устройства при тестах аудиокадров (`NNwb`) не было, поэтому
  формат аудиокадров (G.711 A-law 8 кГц по умолчанию) — предположение. Если звук придёт, первый аудиокадр
  с кодеком и началом данных пишется в лог (`Первый аудиокадр: ...`); по нему нужно проверить и при необходимости
  поменять `AudioFormat`. Пока звука нет, в ffmpeg подаётся тишина, чтобы у плеера всегда была аудиодорожка.
- Звук и видео синхронизируются приблизительно: метки видео берутся с устройства, звук идёт по часам сервера.
- Браузеры не запускают воспроизведение со звуком без действия пользователя, поэтому плеер стартует с выключенным звуком.
- Одно соединение с регистратором и один ffmpeg на всех зрителей. Аутентификации на странице нет — не выставляйте её в интернет.
- Служебные заголовки потока не разобраны полностью; протокол запроса (`toServer720.bin`) не расшифрован.
